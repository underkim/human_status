# Human Status S급 기준 v1 비판적 검토

> 역할: v1 작성자와 독립적인 비판적 리뷰어.

## Blocker

1. **L-E4는 저장소 상태와 외부 CI 상태를 한 항목에 혼합한다.** 워크플로 단계
   존재는 저장소에서 측정 가능하지만 “최신 master 성공”은 GitHub 실행 조회가
   필요하다. 둘 중 하나만 실패해도 원인을 알 수 없다. 분리해야 한다.
2. **L-M3, S-P3~S-P7, S-M1~S-C4는 증적 양식과 유효기간이 없다.** 누가 언제
   어느 SHA에서 확인했는지가 없으면 과거 결과를 현재 release에 재사용할 수 있다.
3. **S-E2의 iOS IPA와 macOS/Linux 빌드를 모든 평가 환경에서 직접 실행하도록
   쓴 것은 실행 가능성 경계를 무시한다.** OS별 runner 증적을 허용하고 같은 SHA,
   도구 버전, artifact hash를 요구해야 한다.
4. **S-M2의 “각 5명·95%”는 10명 표본에서 산술적으로 모순된다.** 20개 과업 중
   19개인지 사용자 성공률인지 정의가 없고, 이 앱의 저장 무결성과도 직접 연결되지
   않는다.
5. **S-M3의 99% 16.7ms는 60Hz 단말에서도 지나치게 엄격하고 측정 도구가
   지정되지 않았다.** 셰이더 컴파일·첫 프레임을 포함할지 불명확하다.

## Should-fix

1. **L-E2의 “1,024 이상”은 테스트 중복 추가로 쉽게 게임화된다.** 테스트 수는
   보조 지표로 두고, 기존 파일 삭제/스킵 증가 여부를 git diff로 함께 확인해야 한다.
2. **L-E1은 한글 경로에서 이미 알려진 Flutter 도구 오류가 난다.** 동일 SHA의
   ASCII-only clone 또는 CI에서 실행하는 공식 절차를 기준에 명시해야 한다.
3. **L-P2의 30초 유지가 정상 동작을 입증하지 않는다.** 시작·설정 진입·퀘스트
   생성/완료·재시작 후 유지까지 최소 스모크를 정의해야 한다.
4. **L-P3와 L-C4가 백업 테스트를 중복한다.** L-P3는 데이터 보존/복원, L-C4는
   사용자 편의 흐름으로 분리하거나 한쪽을 제거해야 한다.
5. **L-M3의 14개 조합 계산이 잘못됐다.** 7화면×2테마×2뷰포트면 28개다.
6. **시장 매력도를 테스트 존재만으로 판정한다.** Human Status 특유의 퀘스트
   완료→XP→레벨업/업적→목표 연쇄와 금융/백업 여정을 명시해야 한다.
7. **S-P6의 “opt-in 정확히 1”은 SDK 재시도나 플랫폼 네이티브 이벤트를 고려하지
   않는다.** 고유 test event ID 1개가 대시보드에 1회 도달하는 것으로 좁혀야 한다.
8. **S-C3의 조건부 제외가 S급 편의성 통과로 읽힐 수 있다.** 플래그가 false면
   기능이 미제공이므로 해당없음 처리 조건과 S급 전체 판정 영향을 명시해야 한다.
9. **해당없음 규칙이 없다.** 지원하지 않는 플랫폼/기능을 임의로 빼서 통과시키지
   못하도록 “공식 지원 범위 밖이고 사용자 노출·광고가 모두 없을 때만” 허용해야 한다.

## Nit

1. 명령의 Windows/Unix quoting 차이를 설명하면 재현성이 좋아진다.
2. 수동 증적은 스크린샷만이 아니라 로그·동영상·콘솔 링크를 허용해야 한다.
3. `git grep`의 구체적 시크릿 패턴은 별도 표로 고정하는 편이 낫다.

## 빠진 차원

- 증적의 SHA 결속, 유효기간, 실행자와 환경.
- 의존성/공급망 검토 및 lockfile 재현성.
- 실제 사용자 데이터의 마이그레이션·이전 백업 복원.
- 장애 시 데이터 손상 없이 재시도·롤백되는지에 대한 명시적 기준.
- 스토어 정책/법무 승인을 코드 품질과 구분하는 최종 Go/No-Go 소유권.
